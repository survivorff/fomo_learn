# 04 · 系统架构拆解

> ⚠️ fomo 未公开后端架构。本文档的分层与服务划分属 **[推断]**，依据是：官方博客对钱包与交易流程的描述、已确认的合作方（Privy / Coinbase / DFlow / Relay / Hyperliquid / Trade[XYZ] / TradingView / Mobula）各自的公开文档约束、以及 17 人团队支撑百万级用户这一事实所隐含的取舍。

---

## 1. 架构第一原理：17 人 / 年化 $200M

理解 fomo 架构的唯一钥匙是这组数字：

| 指标 | 数值 |
|---|---|
| 团队规模（Series B 时） | ~17 人 **[三方 Fortune]** |
| 注册用户 | 190 万+ |
| 月活 | 120 万+ |
| 日活交易者 | 8–10 万+ |
| 月交易量 | $2.8B+ |
| 年化收入 | $200M+ |

**这个比例只有一种可能的架构：执行层全部外采，自研收窄到三件事 —— 客户端体验、社交图谱、链上数据。**

insights4.vc 的判断是：fomo 的大部分执行基础设施来自外部合作方，因此它的潜在护城河不在执行层，而在**执行层之上** —— 身份、交易、粉丝、通知、Thesis、发现历史与声誉之间的连接关系（内容经改写）。

这对自建有直接指导意义：**不要从头造执行层。** 造执行层是 50 人团队两年的事，而且造出来也是商品化的东西。

## 3. 自研 vs 外采边界

这张表是本仓库最重要的一张表。

| 能力 | fomo 的选择 | 为什么 | 自建建议 |
|---|---|---|---|
| **社交图谱**（关注/Feed/Thesis/排行榜/Clan） | **自研** | 唯一的护城河来源；外面没有现成方案 | **必须自研，且要投最多人** |
| **链上数据索引** | 先外采 → **2026-08 收购 Mobula 自研** | 日活上到 10 万 + 多链后，数据延迟与稳定性成为瓶颈 | 先外采（Birdeye/Helius/Moralis/Mobula），量级上来再自建 |
| **持仓 / PnL 计算** | 自研（依赖索引数据） | 与社交层强耦合，口径必须自控 | **自研，且口径一开始就定死** |
| **客户端** | 自研原生 + Web | 体验是核心竞争力 | 自研，移动端优先 |
| **钱包与密钥管理** | **外采 Privy** | 自建 MPC/TEE 是安全高危、合规复杂、投入巨大 | **强烈建议外采**（Privy / Dynamic / Turnkey / Web3Auth） |
| **法币入金** | **外采 Coinbase** | 需要支付牌照、KYC、反欺诈能力 | **必须外采** |
| **DEX 路由聚合** | **外采 DFlow**（Solana） | 已完全商品化 | 外采（Jupiter / DFlow / 1inch / 0x / LiFi） |
| **跨链桥** | **外采 Relay** | 桥是安全高危区，自建等于自建攻击面 | **必须外采** |
| **永续撮合清算** | **外采 Hyperliquid / Trade[XYZ]** | 自建 = 变成交易所 = 牌照地狱 | 必须外采，或干脆不做 |
| **K 线图表** | **外采 TradingView** | 用户已有肌肉记忆 | 外采 |
| **Gas 代付** | 自研策略 + 外采 Bundler/Paymaster | 策略是成本控制点，基础设施是商品 | 策略自研，设施外采 |

### 一句话总结边界

> **凡是「用户能感知差异」且「外面买不到」的，自研；其余全部外采。**

社交图谱和数据是前者，钱包、桥、路由、清算是后者。

## 4. 四个核心服务详解

### L3-a 社交服务（护城河）

职责：
- 关注关系图谱（含互关识别）
- Feed 生成与排序（全局 / 关注 / Clan / 代币四种）
- Thesis 存储与 K 线时间轴对齐
- 评论树 + 表情回应
- 排行榜计算（多时间窗 × 三种主体）
- Clan 成员管理与周榜
- 通知扇出（**这是最大的技术挑战**）
- 分享卡渲染

**通知扇出的规模问题**：头部交易者有六位数粉丝。他开一个仓，要在秒级向十万人推送。这是典型的**大 V 扇出问题**，需要：
- 推拉结合（大 V 走拉模式，普通用户走推模式）
- 推送优先级与去重（同一个人连续买 5 笔不能推 5 条）
- 用户级推送频控（否则用户直接关通知）

详见 [07 社交图谱与数据体系](07-社交图谱与数据体系.md)。

### L3-b 交易编排服务

职责：把「用户滑了一下」翻译成一条或多条链上交易，并保证最终一致。

```
接单
 │
 ├─ 1. 解析目标：代币在哪条链？需要跨链吗？
 ├─ 2. 报价聚合：查聚合器（Solana→DFlow）/ 跨链（Relay）
 ├─ 3. 成本核算：路由成本 + Gas（平台承担）+ 平台费
 ├─ 4. 风控前置：余额、限额、代币安全标记、滑点上限
 ├─ 5. 交易构造：
 │      EVM     → ERC-4337 UserOperation（+ Paymaster 签名）
 │      Solana  → 原生 Transaction（+ 平台付优先费）
 ├─ 6. 签名：调 Privy → TEE 内重组密钥 → 签名 → 销毁
 ├─ 7. 提交：Bundler（EVM）/ RPC + DFlow（Solana）
 ├─ 8. 状态机：pending → submitted → confirmed / failed
 │      失败重试、优先费升档、超时回滚
 └─ 9. 成功 → 发事件 → 触发索引/持仓/Feed/通知
```

**第 8 步是最容易被低估的地方。** Memecoin 交易在高波动时段失败率很高（Solana 拥塞、滑点超限、报价过期）。fomo 被投诉「卖不出去」基本都源于此。必须做的事：

- 交易状态机持久化（不能只存内存）
- 优先费动态升档策略
- 幂等保证（用户重复点不能重复下单）
- 失败原因对用户可读（不要直接甩链上错误码）
- 部分成交处理

### L3-c 数据索引服务（2026-08 起自研）

这是 fomo 最新的战略投入。Odaily 把问题描述得很清楚（内容经改写）：新代币出现时，应用要识别合约地址、名称和所属网络，并持续读取交易、流动性、价格、持币地址与钱包行为，再把不同链的原始记录整理成用户能看懂的数据。

管道：

```
多链节点/RPC ──► 区块订阅（WebSocket / gRPC）
                     │
                     ├─► 事件解析（按链按 DEX 解码 Swap / Transfer / LP 事件）
                     ├─► 代币元数据发现（新币：名称/符号/小数位/图标/社交链接）
                     ├─► 价格计算（池子加权 / 参考 oracle）
                     ├─► 流动性与持币分布
                     ├─► 钱包行为归因（哪个 fomo 用户做的？）
                     │
                     ├─► 热数据：Redis / 内存（实时价格、当前持仓）
                     ├─► 时序数据：K 线、PnL 曲线（ClickHouse / TimescaleDB）
                     └─► 关系数据：持仓、成交、成本基准（Postgres）
                              │
                              └─► WebSocket 推送给客户端
```

**为什么必须自研（当量级到了）**：
1. 延迟 —— 社交交易的卖点是「他买的那一刻你就知道」，秒级延迟即失效
2. 新链接入速度 —— fomo 的交易量高度跟随链上热点（Robinhood Chain 三个月内吃到 75% 份额），三方数据商未必第一时间支持新链
3. 成本 —— 10 万日活 × 实时价格订阅，三方 API 账单会失控
4. 数据独占 —— 归因后的用户行为数据是社交图谱的原料

**但对自建项目：第一年一定外采。** Birdeye / Helius / Moralis / Mobula / Codex 都能用。自建索引是 5–8 人的长期投入。

### L3-d 账户与资金服务

职责：身份、钱包编排、余额归集、入出金、风控、费率与推荐关系。

关键设计点：
- **余额归集**：用户看到一个美元数字，实际是 N 条链上的 USDC 余额之和 + 持仓市值。归集逻辑要处理链间不一致、待确认交易、跨链在途资金
- **费率引擎**：0.5% / $0.95 最低 / 推荐码 -10% / Perps 0.05% —— 规则要可配置，不能硬编码
- **Referral 结算**：25% 分成需要精确的归因链路和对账能力

## 5. 关键技术决策及其代价

| 决策 | 收益 | 代价 | 承担者 |
|---|---|---|---|
| **嵌入式钱包（无助记词）** | 30 秒开户 | 依赖 Privy 可用性；密钥模型比助记词复杂；用户不导出私钥则丢设备可能永久失去资产 | 用户 |
| **USDC 统一余额** | 心智简单、PnL 直观 | 脱锚/发行方/合约风险；每笔交易隐含一次兑换 | 用户 |
| **Gas 代付** | 转化率大幅提升 | Gas 价格飙升时成本失控；被刷的风险；**小额交易单位经济为负** | 平台 |
| **收窄交易面（无限价单、低滑点控制）** | 认知负担低 | 责任转移给平台默认值；专业用户流失 | 平台 + 用户 |
| **执行层全部外采** | 17 人跑到年化 $200M | 单点依赖；合规限制传导（Perps 屏蔽美国）；护城河不在执行层 | 平台 |
| **社交默认公开** | 内容供给自动解决 | 羊群效应、出货流动性、时间尺度被压缩 | 用户 |
| **不做 KYC** | 开户无摩擦、全球可达 | 监管不确定性；合规压力堆在支付方与地域屏蔽上 | 平台 |

### 最值得警惕的一条：Gas 代付 + $0.95 最低费

这两个设计是一对的。Gas 代付让平台承担成本，$0.95 最低费是为了让小额交易不亏。但后果是 **$10 的单子显性费用 9.5%** —— 这是把区块链的复杂度换成了消费者的高昂代价（[insights4.vc](https://insights4vc.substack.com/p/fomo-behind-the-75m-series-b-from) 的原意，措辞已改写）。

自建时要做的量化：**画出「交易金额 × 实际费率」曲线**，明确哪个区间是亏损区、哪个区间用户会流失。详见 [08 费用结构与商业模式](08-费用结构与商业模式.md)。

## 6. 单点依赖风险图

```
                       ┌─────────────┐
                       │   Privy     │ ← 挂了：无法登录、无法签名 = 全站停摆
                       └──────┬──────┘
                              │ P0
    ┌──────────────┬──────────┴───────┬──────────────┐
    │              │                  │              │
┌───▼────┐   ┌─────▼─────┐   ┌────────▼──────┐  ┌───▼──────┐
│Coinbase│   │  DFlow    │   │    Relay      │  │Hyperliquid│
│ Onramp │   │  路由      │   │   跨链桥       │  │  + TradeXYZ│
└────────┘   └───────────┘   └───────────────┘  └───────────┘
   P1            P0               P1                 P1
 挂了：法币      挂了：Solana      挂了：统一余额      挂了：Perps
 入金不可用      交易不可用        失效、跨链中断      不可用
```

缓解措施（fomo 是否做了未知，**自建必须做**）：

| 依赖 | 缓解方案 |
|---|---|
| 钱包服务 | 多供应商抽象层；密钥导出兜底；降级到只读模式 |
| 路由聚合 | **至少接两家**（如 Jupiter + DFlow），自动 failover |
| 跨链桥 | 多桥路由；单桥故障时降级为「仅支持该链内交易」 |
| 法币入金 | 多通道（Coinbase / MoonPay / Stripe / Transak） |
| Perps | 场馆故障时明确提示，并保证已有仓位的可见性 |
| 数据索引 | 三方 + 自建双写，互为校验 |

⚠️ 一个真实变数：**DFlow 在 2026-05 被 MoonPay 以约 $100M 全股票收购** **[三方 iq.wiki]**。被收购的基础设施商的服务条款、定价和优先级都可能变化。这正是单点依赖的现实风险。

## 7. 实时性架构（社交交易的生死线）

社交交易的核心承诺是「他买的那一刻你就知道」。这个承诺的技术兑现路径：

```
链上出块
   │  ≤1s（Solana）
   ▼
索引服务捕获 Swap 事件
   │  目标 <500ms：解析 + 归因到 fomo 用户
   ▼
持仓服务更新 + PnL 计算
   │  目标 <200ms
   ▼
社交服务写 Feed + 触发扇出
   │  推：小粉丝量直接写收件箱
   │  拉：大 V 由读端合并
   ▼
通知网关 → APNs / FCM  ＋  WebSocket 推活跃客户端
   │  目标端到端 <3s
   ▼
用户手机震动 → 点开 → 两次点击建仓
```

**端到端目标应设在 3 秒以内。** 超过这个数，跟随者拿到的价格已经明显劣于领头者，产品承诺就破了。

这也解释了为什么 fomo 要把数据索引自研 —— 这条链路上任何一个外部 API 调用都是不可控的延迟来源。

## 8. 自建架构建议（精简版）

如果目标是 6 个月内做出可用产品：

```
第一阶段（MVP，约 8–10 人）
├── 客户端：React Native（一套代码出双端）+ Next.js Web
├── 后端：单体优先，模块化切分（不要一开始上微服务）
│     语言建议 Go 或 TypeScript（Node）；数据密集部分用 Rust 也行
├── 钱包：Privy（直接买，不要自建）
├── 入金：MoonPay / Transak（比 Coinbase Onramp 好接）
├── 路由：Jupiter（Solana）+ 0x/LiFi（EVM）
├── 跨链：Relay 或 LiFi
├── 数据：Birdeye / Helius（Solana）+ Codex/Moralis（EVM）
├── 存储：Postgres（关系）+ Redis（热数据）+ ClickHouse（时序/K线）
├── 实时：WebSocket 网关 + Redis Pub/Sub
└── 图表：TradingView Charting Library（需授权）

第二阶段（社交层深化，+5 人）
├── Feed 排序算法
├── 通知扇出优化（推拉结合）
├── 排行榜实时计算
└── Thesis / Clan

第三阶段（数据自研，+5–8 人）
└── 自建多链索引管道，替换三方 API
```

**不要在第一阶段做的事**：自建索引、自建钱包、自建桥、上 Perps、做限价单。

详细排期见 [11 自建路线图与技术选型](11-自建路线图与技术选型.md)。
