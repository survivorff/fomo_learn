# 05 · 账户与钱包体系

> 本文档的主要一手来源是 fomo 官方博客《How fomo Keeps Your Crypto Secure: Wallet Architecture and Security Explained》（2026-03-04）：<https://fomo.family/blog/learn/fomo-security-wallet-architecture>。这是 fomo 唯一一篇技术性官方文档。

---

## 1. 核心命题：既要无助记词，又要自托管

传统上这两件事是矛盾的：

| 模型 | 谁控制私钥 | 用户体验 | 风险 |
|---|---|---|---|
| **托管型**（CEX） | 平台 | 好（邮箱密码即可） | 平台被黑 / 破产 / 冻结你的账户 = 资产有风险 |
| **非托管型**（传统钱包） | 用户（助记词） | 差（抄 12/24 词并妥善保存） | 助记词丢失 / 被拍照 / 被钓鱼 |

fomo 要的是「托管型的体验 + 非托管型的安全」。它的解法是**嵌入式钱包 + 密钥分片**。

官方表述的关键一句（措辞已改写）：私钥被分片并分散存储，**没有任何单一方（包括 fomo 自己）能够访问用户资金**。

```
└─────────────────────────────────────────────────────────────┘
```

## 3. Shamir's Secret Sharing 为什么可行

**[官方]** fomo 明确点出 SSS 是成熟技术，1Password、Cloudflare 等在高安全场景中已使用多年。

### 原理（简化）

把一个秘密 $S$ 编码为多项式的常数项，在多项式上取 $n$ 个点分发出去。任意 $k$ 个点（$k \le n$）可以唯一重建这个多项式，从而恢复 $S$；少于 $k$ 个点则**在信息论意义上**得不到任何关于 $S$ 的信息 —— 不是「算不出来」，是「数学上不存在信息」。

### 关键设计参数

| 参数 | 含义 | fomo/Privy 的选择 |
|---|---|---|
| $n$ | 总分片数 | 未公开（至少 3） |
| $k$ | 重建阈值 | 未公开 |
| 分片分布 | 谁持有哪片 | 用户设备 + Privy + 恢复方 **[推断]** |

**「用户始终保有足够分片来独立访问」这句官方表述是整个安全模型的关键。** 它意味着 $k$ 的组合里必须包含至少一个「用户可独立凑出」的路径，否则就不是自托管而只是「名义上非托管」。

### 与 MPC 的区别

| | Shamir 分片 | MPC / TSS |
|---|---|---|
| 签名时是否重建完整密钥 | **是**（在 TEE 内短暂重建） | **否**（各方用分片各自计算签名片段） |
| 安全边界 | 依赖 TEE 的完整性 | 不依赖单点重建 |
| 实现复杂度 | 较低 | 较高，且不同签名算法需不同协议 |
| 攻击面 | TEE 被攻破的瞬间 | 多方共谋 |

fomo/Privy 走的是 **Shamir + TEE**，不是 MPC。这是工程可行性与安全性的权衡：TEE 提供硬件隔离，密钥只在受保护的隔离环境中以完整形态存在极短时间。

⚠️ **这个模型的信任假设是 TEE 的完整性**（通常是云厂商的 Nitro Enclaves / SGX / Confidential VM）。自建时要明确这一点，不要宣传成「零信任」。

## 4. ERC-4337 智能账户带来什么

**[官方]** fomo 在 EVM 链上用符合 ERC-4337 账户抽象标准的智能合约钱包。三个直接能力：

### 4.1 Gas 代付（Gas Sponsorship）

Paymaster 合约替用户付 Gas。用户在 Base 上交易不需要持有 ETH，在 BNB Chain 上不需要持有 BNB。

**这是产品体验的最大杠杆之一**，但成本由平台承担 —— 见 [08 费用结构](08-费用结构与商业模式.md)。

### 4.2 交易批处理（Batching）

多个操作打包成一笔链上调用。官方说这让复杂交易更快更高效；insights4.vc 指出**批处理也是让 Gas 代付在规模上经济可行的原因**（把多次固定开销摊薄）。

### 4.3 统一余额的实现基础

单一美元余额能跨全部链工作，是因为智能钱包基础设施替用户处理了跨链复杂度。用户只需入金一次（Apple Pay / 借记卡 / 加密充值），就能立刻在任意支持链上交易。

### Solana 侧的差异

Solana 没有 ERC-4337。它的 Gas（含优先费）极低，平台代付的实现方式不同 —— 通常是**平台作为 fee payer 签名，或通过 relayer 代为提交** **[推断]**。

⚠️ 自建时注意：**Solana 与 EVM 的账户模型、Gas 模型、代付机制完全不同**，「一套钱包打通所有链」在产品层是一个地址映射问题，在工程层是两套实现。

## 5. 一笔交易的签名时序

**[官方描述 + 推断细节]**

```
用户滑动买入
    │
    ▼
① 客户端 → 后端：下单请求
    │
    ▼
② 交易编排服务：报价 → 路由 → 构造未签名交易
    │   EVM:    UserOperation（含 Paymaster 签名）
    │   Solana: Transaction（平台作为 fee payer）
    ▼
③ 调用 Privy 签名接口（带用户会话凭证 + 设备侧分片）
    │
    ▼
④ ┌─────── TEE 内（硬件隔离） ────────┐
   │  收集分片 → 重建完整私钥            │
   │  对交易做签名                       │
   │  立即销毁内存中的密钥                │
   └────────────────────────────────┘
    │  ★ 密钥以完整形态存在的时间 = 毫秒级
    ▼
⑤ 返回签名 → 提交上链
    │   EVM:    Bundler → EntryPoint 合约
    │   Solana: RPC，经 DFlow 路由缓解三明治
    ▼
⑥ 确认 → 索引 → 更新持仓与 PnL → 写 Feed → 推送粉丝
```

官方对这个流程的总结是：从用户视角像在任何 fintech App 里点了个按钮，但背后是用自己的密钥在去中心化区块链上完成了一笔自托管的链上交易。

## 6. 安全边界：这个模型防得住什么、防不住什么

### ✅ 防得住

| 攻击 | 为什么被消除 |
|---|---|
| 助记词被钓鱼 | 没有助记词 |
| 助记词被截图 / 明文存储 | 同上 |
| SIM-swap | 认证用邮箱/Apple ID，不用手机号 |
| 无限额合约授权被滥用 | 不需要用户签 blanket approval |
| 平台跑路 / 冻结账户 | 平台无法单方面重建密钥；可导出私钥 |
| 拿到已解锁手机就提走资金 | 出金和导出密钥都强制 FaceID |
| 平台被黑导致资产被盗 | 平台不持有完整密钥 |

### ❌ 防不住（必须在产品中明示）

| 风险 | 说明 |
|---|---|
| **邮箱账户被攻破** | 邮箱是钱包的入口。fomo 自己建议：邮箱要用强密码 + 开启双因素 |
| **设备丢失且从未导出私钥** | fomo 无法恢复访问权。Datawallet 明确提示这种情况可能**永久损失余额** |
| **TEE 被攻破** | 这是信任假设的根 |
| **Privy 服务不可用** | 无法登录、无法签名 = 全站停摆（见 [04 单点依赖](04-系统架构拆解.md#6-单点依赖风险图)） |
| **智能合约风险** | ERC-4337 账户、Paymaster、路由合约都有代码风险 |
| **交易一旦上链无法撤销** | 非托管的必然结果：fomo 不能撤销交易、不能恢复丢失设备的访问权、代币归零不赔 |
| **代币本身归零** | 自托管不保护你不买垃圾 |
| **导出的私钥** | 条款注明导出的密钥材料由 Privy 传输，安全责任归用户 |

### 一个必须诚实的定性

insights4.vc 给出的定义最准确（措辞已改写）：这套架构应该叫**嵌入式自托管（embedded self-custody）**，而不是传统的托管型券商账户，也不完全等同于「用户独占密钥」的经典自托管。

自建产品在宣传上不要越过这条线。

## 7. fomo 官方给用户的安全建议

**[官方]** 直接可以抄进自建产品的安全中心：

1. **保护好邮箱** —— 它实际上是钱包的入口。用强密码 + 开启双因素
2. **保持生物识别开启** —— 不要为了方便关掉
3. **谨慎处理导出的私钥** —— 按银行密码级别对待，不分享、不明文存、不截图
4. **警惕钓鱼** —— 平台**永远不会**通过邮件、私信或任何渠道索要私钥、密码或助记词
5. **保持设备系统更新**

另外要补一条 fomo 自己踩过的坑：**核对开发者名与官方域名**。存在 `fomoo.family`（双 o）的仿冒站点会清空连接的钱包 **[三方]**，App Store 上也有克隆 App。自建产品应在官网首屏和 App 内显著位置放官方域名/开发者名核验提示。

## 8. 官方 FAQ 要点（可直接映射到自建产品的帮助中心）

| 问题 | fomo 的回答（措辞已改写） |
|---|---|
| 是托管还是非托管？ | 完全非托管，平台无法访问、转移或冻结资产 |
| 平台关停后资金怎么办？ | 资产在链上、由用户密钥控制，可导出密钥用任意兼容钱包访问 |
| 需要抄助记词吗？ | 不需要。但可随时导出私钥做备份 |
| FaceID 用在哪？ | 打开 App、授权出金、授权导出私钥 |
| Gas 怎么处理？ | 平台代付，用户无需持有原生代币 |
| 能多设备登录吗？ | 能，账户绑邮箱/Apple ID；**生物识别设置按设备生效** |
| 个人信息上链吗？ | 不上链。链上只有钱包地址和交易数据；邮箱与身份由链下认证系统处理 |

## 9. 自建选型建议

### 钱包基础设施：不要自建

| 方案 | 特点 | 适用 |
|---|---|---|
| **Privy** | fomo 在用；Shamir + TEE；嵌入式钱包 + 法币 Onramp 一体；支持 Solana + EVM | **首选**，功能覆盖最接近目标 |
| **Turnkey** | TEE 优先、策略引擎强、面向需要精细权限控制的场景 | 需要复杂签名策略时 |
| **Dynamic** | 嵌入式 + 外部钱包连接体验好 | 需要同时支持自带钱包的场景 |
| **Web3Auth (Torus)** | MPC 路线、生态成熟 | 偏好 MPC 而非 Shamir 时 |
| **Coinbase Embedded Wallets** | 与 Coinbase 生态（含 Onramp）打通紧 | 重度依赖 Coinbase 通道时 |

**自建 MPC/TEE 密钥系统的真实成本**：3–5 名密码学/安全工程师 + 12 个月 + 第三方审计 + 持续的安全运维。而且一旦出事就是资产级事故。**这笔钱花在社交图谱上回报高得多。**

### 账户模型建议

```
EVM 侧：ERC-4337 智能账户
  ├── Bundler：Pimlico / Alchemy / Biconomy / ZeroDev
  ├── Paymaster：同上，或自建以控制成本策略
  └── 建议用 ERC-7579 / Kernel 一类模块化账户，留后续扩展余地

Solana 侧：原生账户 + 平台 fee payer
  └── 注意与 EVM 侧的地址映射关系要在账户服务里统一管理
```

### 必须一开始就做对的三件事

1. **密钥导出功能不能延后。** 它是「自托管」主张的唯一硬证据，也是用户信任的基础。
2. **生物识别的场景划分要和 fomo 一致。** 交易不卡、出金必卡。这个非对称是经过验证的。
3. **多设备与账户恢复流程要设计清楚。** 这是嵌入式钱包最容易出用户投诉的地方 —— 「换手机了怎么办」必须有明确答案。
